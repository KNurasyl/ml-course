# M11 — оценивание и проверка модельного judge

```powershell
Set-Location C:\projects\ml-llm-course
.\.venv\Scripts\python.exe labs\M11\demo.py
```

Python3.11.9, NumPy2.4.6, sklearn1.9.1; для настоящего judge используются torch2.15.0+cpu и transformers4.57.6 из M09. GPU и платный API не нужны. Локальные веса SmolLM должны быть подготовлены по инструкции M09. Модель работает на CPU, нужно несколько свободныхGBRAM. Шесть коротких генераций могут занять десятки секунд в зависимости от нагрузки.

Для отдельного изучения арифметики без модели:

```powershell
.\.venv\Scripts\python.exe labs\M11\demo.py --metrics-only
```

`hr.jsonl` и `backend.jsonl` содержат по10авторских синтетических случаев с вопросом, ответом, критериальными оценками и объяснением. [Рубрики](rubrics.md) описывают шкалы. Это не реальные ответы участников. `scenario_id` разделяет группы между development и check; после чтения ключа check становится знакомым и требует нового независимого набора для итоговой проверки.

Первая часть demo использует явно заданные массивы correctness для арифметики. Ожидается baseline0.5, candidate0.75, прирост0.25; исправления2,4,8, регрессия3. Поскольку case3критический, `release_allowed=false`. Парный percentile bootstrap: seed17,5000повторов, наблюдавшийся интервал[-0.25,0.75]. Он демонстрирует неопределённость малого набора, а не доказывает качество реального интервьюера. Kappa учебных оценщиков≈1/3; confusion matrix `[[1,1],[1,1]]`.

Вторая часть действительно вызывает SmolLM на четырёх технических ответах и двух порядках пары. Сохраняются raw_result, parsed, ручная ожидаемая оценка и совпадение. В авторском прогоне0из4ответов прошли строгую JSON-схему: coverage0, agreement_on_valid=null, correct_over_all0. Это подтверждённое ограничение этой маленькой модели как judge в данном протоколе. Невалидные ответы не заменены эталонными метками и не исключены из общего знаменателя.

Все результаты — `artifacts/M11/report.json`. Посмотри сырые тексты и перестановки до общего числа. Добавь новые случаи и собственную независимую разметку. Успешный запуск расчёта не означает освоение навыка, проведённый пилот или карьерную готовность.


## Обязательный интеграционный опыт M11-L06

`demo.py` выше изучает арифметику и ограничения judge. Проверку настоящих ответов тренажёра выполняет отдельный `evaluate.py`: он не подставляет заданные correctness вместо вывода модели.

```powershell
.\.venv\Scripts\python.exe labs/M11/evaluate.py collect --cases labs/M11/cases-v3.jsonl --out artifacts/my-M11-run
```

В новой папке появятся неизменённые `outputs.jsonl`, версии/хэши `run.json` и пустая таблица оценок. Заполни её по рубрике M11-L06, сохрани отдельно как `annotations.jsonl`, затем:

```powershell
.\.venv\Scripts\python.exe labs/M11/evaluate.py score --run artifacts/my-M11-run --annotations artifacts/my-M11-run/annotations.jsonl
```

Сбор использует локальную Qwen из эталонного проекта; первая загрузка бесплатных весов требует сети. Повторный сбор в занятую папку запрещён, чтобы не потерять исходные ответы. Отсутствующая оценка является ошибкой протокола, а не нулём. Нужна содержательная разметка HR и backend отдельно; её нельзя автоматически вывести из наличия цитаты. [Измеренный разбор двух попыток](../../course/feedback-case-study.md) и файлы в `quality/evaluation` доступны без нового запуска LLM. Это авторская разметка с AI, не независимое исследование пользователей.

## Дополнение версии 1.2.0: error analysis как процесс (T37, урок M11-L07X)

```powershell
.\.venv\Scripts\python.exe labs\M11\error_analysis.py report
.\.venv\Scripts\python.exe -m pytest -q tests\regression
```

`report` читает замороженные трассы и коды из `quality/error-analysis` и работает без моделей. Он пересчитывает сигналы по ответам и считает таксономию: долю с интервалом Уилсона и первую ошибку по конвейеру. Затем сверяет каждую автоматическую проверку с ручным кодом (точность, полнота, пропуски) и считает причину `cites_prompt_example`. Отчёт пишется в `artifacts/M11/error-analysis/report.json`.

`collect` собирает трассы заново и требует llama.cpp и GGUF из T30. Вопросов 66 (52 ru-embed-1 и 14 диагностических 1.1.0), поиск лексический и детерминированный (RRF символьного TF-IDF и BM25, три абзаца). Отвечает Qwen2.5-0.5B Q4_K_M со ссылками [id] и фразой отказа, генерация жадная. По умолчанию результат пишется в `artifacts/M11/error-analysis`, чтобы не затереть замороженный набор.

Коды в `codes.json` поставил автор курса за один проход после чтения каждой трассы целиком. Кодировщик один, согласие не измерялось.

Регрессионный набор `tests/regression/test_rag_regression.py` проверяет:
- поиск для всех 66 вопросов не изменился;
- точность и полнота проверок не упали;
- опасная трасса p-permission по-прежнему ловится;
- верные ответы не вызывают тревоги;
- prompt-контракт не изменился.

Медленный тест с `$env:M11_LIVE = '1'` заново спрашивает модель по шести контрольным трассам.

Авторский прогон 06.11.2026: верно 3 из 66; нет ответа — 43 (первая ошибка в 33); неверная ссылка — 18, из них 15 из-за примера `[index-v2-c1]` в системном prompt. Лишний отказ — 10, нет отказа — 10, промах поиска — 8, мимо вопроса — 5, выдуманное утверждение — 2, формат — 2. Заготовленные категории «нет ссылки» и «потеряно условие» не встретились. Полнота проверок: промах поиска 0.75, нет отказа 0.50, неверная ссылка 0.94, остальные 1.0 (правила писались по этим же трассам). Тесты модуля — `tests/test_error_analysis.py`.

## Дополнение версии 1.2.0: promptfoo поверх собственного harness (T38, урок M11-L06)

```powershell
.\.venv\Scripts\python.exe labs\M11\promptfoo_eval.py run
.\.venv\Scripts\python.exe -m pytest -q tests\test_promptfoo_eval.py
```

Нужны Node.js 22.22 или новее (с npx), llama.cpp и GGUF из M09-L07X. `run` поднимает два llama-server на 127.0.0.1: tiny (Qwen2.5-0.5B, порт 18080) и strong (Qwen3.5-4B, порт 18081). Затем запускает `npx --yes promptfoo@0.124.1 eval` с выключенными телеметрией и проверкой обновлений. Первый запуск скачивает promptfoo в кэш npm: у автора 1.4 ГБ. База и логи promptfoo лежат в `artifacts/M11/promptfoo/home`. Флаг `--profiles tiny` оставляет один профиль, `--first 4` — первые четыре случая.

Файлы в `labs/M11/promptfoo`:
- `promptfooconfig.yaml` — профили, запрос как в режиме prompt_only M09-L08X и три проверки;
- `checks.js` — контракт M09-L05 на JavaScript и совпадение оценки с эталоном;
- `prompt.json`, `cases.jsonl`, `feedback.schema.json` — генерируются из `labs/M09/structured_output.py` командой `promptfoo_eval.py sync`, вручную их не правят.

После прогона обёртка пересчитывает каждую проверку на Python и пишет `artifacts/M11/promptfoo/comparison.json`. В нём число прохождений по promptfoo и по Python, все расхождения и совпадение текстов с прогоном T31. `compare` повторяет сверку по готовому `results.json` без моделей.

Тесты сверяют:
- сгенерированные файлы с Python;
- конфиг с запросом T31;
- JS-контракт с Python на 20 краевых строках в настоящем Node; без Node эти два теста пропускаются.

Авторский прогон 06.11.2026: tiny — схема и контракт 21/24, оценка верна в 9; strong — 24/24 и 18. Расхождений с Python 0 из 144 вердиктов, все 48 ответов совпали с T31. Весь прогон занял 4 мин 4 с; promptfoo вышел с кодом 100, потому что часть тестов не прошла.
