# M10 — поиск и настоящий RAG

```powershell
Set-Location C:\projects\ml-llm-course
.\.venv\Scripts\python.exe labs\M10\demo.py
```

Восемь документов созданы для курса на английском языке и находятся в `CORPUS` в demo.py; происхождение записано у каждого фрагмента. Запросы и релевантные ID заданы явно. Это небольшой development-набор для изучения механики, не репрезентативный benchmark.

Проверено: Python3.11.9, NumPy2.4.6, sklearn1.9.1, torch2.15.0+cpu, transformers4.57.6. CPU,2 потока, без платных сервисов. Сначала загружается encoder, затем освобождается и запускается SmolLM из M09; тяжёлые модели не держатся одновременно намеренно. Для комфорта оставь несколько GB свободной RAM. GPU не нужен.

Реальный pretrained encoder: [sentence-transformers/all-MiniLM-L6-v2](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2), Apache2.0, revision `1110a243fdf4706b3f48f1d95db1a4f5529b4d41`, скачанные файлы 91578299 байт. Используются masked mean pooling и L2-нормировка,384 координаты, максимум 256 токенов. Это английская модель: качество русского поиска не обещано. Файлы находятся в `models/all-MiniLM-L6-v2`, provenance и карточка сохранены.

Если encoder отсутствует:

```powershell
.\.venv\Scripts\python.exe labs\M10\demo.py --download
```

Эта команда скачивает только encoder; для отсутствующей SmolLM сначала выполни команду загрузки из M09. После скачивания оба компонента работают локально. Для изучения только поиска без загрузки генератора:

```powershell
.\.venv\Scripts\python.exe labs\M10\demo.py --retrieval-only
```

Сравниваются пять путей: разреженный TF-IDF; плотный LSA размерности 4; настоящий MiniLM; RRF двух поисков; прозрачный эвристический reranker по покрытию терминов. LSA не называется pretrained semantic encoder, а reranker не называется cross-encoder. Отчёт показывает все ранги и метрики по каждому запросу, поэтому можно увидеть различия даже при одинаковом среднем.

Инварианты: embedding имеет форму `[число текстов,384]`, нормы≈1, RRF для учебных списков даёт правильный порядок, источник атомарности входит в переданный контекст. Реальная генерация получает этот контекст через SmolLM. В авторском прогоне ответил: «If one operation fails, the transaction changes are rolled back together.» Источник был использован по смыслу, но ссылка не появилась: `has_citation=false`. Проверка не скрывает это ограничение.

`artifacts/M10/report.json` содержит traces, context, extractive_baseline и generated_answer раздельно. Поле `citation_ids_known` проверяет только существование указанных ID; если ссылок нет, оно может быть истинно для пустого множества, поэтому обязательно читать `has_citation` отдельно. Подтверждённость требует ручного разбора утверждений. Нельзя выдавать extractive baseline за текст LLM.

Добавь собственные перефразирования и случай без источника. Сначала отметь, что именно потерял поиск, затем исследуй генерацию с oracle context. Результат на семи авторских запросах не является оценкой качества на реальных интервью.

## Дополнение версии 1.2.0: векторное хранилище (T34, урок M10-L08X)

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-optional.in
.\.venv\Scripts\python.exe labs\M10\vector_store.py --no-pg
```

Эталон — точный поиск в памяти (`exact_topk`: косинусное расстояние во float64, ничья по меньшему id). Хранилище sqlite-vec 0.1.9 (`SqliteVecStore`) — один файл SQLite с таблицей `store_meta`, где записаны эмбеддер и размерность, и таблицей vec0 с колонкой группы; запрос от другого эмбеддера вызывает `EncoderMismatch`. Часть «курс» кладёт 72 абзаца корпуса M10-L06 с векторами первого скачанного эмбеддера (USER-bge-m3, иначе MiniLM), закрывает и снова открывает файл и сверяет top-5 64 запросов из M10-L07X с эталоном. Если скачаны другие модели той же размерности, она же считает, что вернул бы поиск их запросами без проверки эмбеддера. Часть «синтетика» — 20 000 векторов d = 128 вокруг 64 центров, 200 запросов, группа фильтра около 1 % строк, k = 10. Отчёт — `artifacts/M10/vector_store/report.json`, тесты — `tests/test_vector_store.py`. Без sqlite-vec лабораторная отмечает `not_installed`.

pgvector — по желанию, без прав администратора и без изменений в установленном PostgreSQL:

```powershell
.\.venv\Scripts\python.exe labs\M10\pg_local.py build
.\.venv\Scripts\python.exe labs\M10\pg_local.py init
.\.venv\Scripts\python.exe labs\M10\pg_local.py start
.\.venv\Scripts\python.exe labs\M10\vector_store.py
.\.venv\Scripts\python.exe labs\M10\pg_local.py stop
```

`build` скачивает исходники pgvector 0.8.7 с GitHub (сверяет sha256) и собирает их через `nmake` из Visual Studio с компонентом C++ в `artifacts/M10/pgvector/ext`; цель `install` не вызывается, потому что она пишет в Program Files. `init` создаёт кластер PostgreSQL 18 в `artifacts/M10/pgdata` на 127.0.0.1:55433 с пользователем `course` и подключениями без пароля — только для синтетических данных курса. Расширение подключается параметрами `extension_control_path` и `dynamic_library_path`, поэтому нужен PostgreSQL 18. `start` запускает postgres отдельным процессом со скрытой консолью: при запуске через `pg_ctl` из терминала новые подключения после закрытия терминала падали с кодом 0xC0000142. Лабораторная обращается к серверу через `psql` (Python-драйвер не нужен), работает в схеме `m10_l08x` и измеряет время внутри сервера функцией PL/pgSQL. Свой сервер с pgvector подключается флагом `--pg-conninfo` без пароля — libpq берёт его из pgpass. Недоступный сервер отмечается в `status`, лабораторная не падает.

Авторский прогон 05.11.2026 (CPU, около 70 с): sqlite-vec после переоткрытия и pgvector без индекса совпали с эталоном до порядка во всех 64 запросах курса. Для 72 строк планировщик не взял HNSW. Запросы Qwen3-Embedding-0.6B той же размерности 1024 без проверки эмбеддера дали 2 попадания из 24 на перефразированных вопросах против 19 у USER-bge-m3; запросы bge-m3 — 20, потому что USER-bge-m3 дообучен из bge-m3. На синтетике HNSW при ef_search = 10, 40, 100 дал recall@10 0.934, 0.999, 1.000 за 0.17–0.30 мс против 4.58 мс у полного перебора. С фильтром на 1 % строк планировщик выбрал HNSW и вернул в среднем 0.49 строки вместо 10; `hnsw.iterative_scan = relaxed_order` вернул 10 строк (recall 0.939, 3.0 мс), B-tree по группе — точный ответ за 0.20 мс. На почти бесструктурных данных (разброс 3.0, добавлены после пробного прогона) HNSW при ef_search = 100 нашёл 76 % соседей. Это синтетика и учебный корпус, а не сравнение продуктов.

## Дополнение версии 1.2.0: cross-encoder для reranking (T35, урок M10-L09X)

```powershell
.\.venv\Scripts\python.exe tools\download_models.py --rerankers
.\.venv\Scripts\python.exe labs\M10\rerank.py
```

Первая команда один раз скачивает bge-reranker-v2-m3 (BAAI, Apache-2.0, 2.27 ГБ, ревизия 953dc6f из `metadata/reference-models.json`). Вторая берёт корпус и запросы T32 (72 абзаца, 24 перефразированных вопроса, 24 с термином, 4 без ответа и 12 вопросов 1.1.0) и три первые стадии: RRF символьного TF-IDF и BM25, MiniLM и USER-bge-m3, если он скачан. Пул каждой — 20 фрагментов. Вторые этапы на одном пуле: порядок первой стадии, эвристика покрытия слов из `demo.py`, перенесённая на русские слова, и cross-encoder. Эвристика 1.1.0 в `demo.py` не менялась. Метрики документные, `in_pool` — candidate Recall@20. Cross-encoder оценивает все 64 × 72 пары один раз: пулы — их подмножества, перебор всего корпуса — верхняя граница. Логиты сохраняются в `pair_logits`, так что другие N считаются без повторного запуска модели. Задержка меряется отдельно для N = 5, 10, 20, 40 на одних и тех же 16 запросах. Отчёт — `artifacts/M10/rerank/report.json`. Флаги: `--no-reranker`, `--no-dense`, `--no-minilm`, `--threads` (по умолчанию 4). Без модели лабораторная отмечает `not_downloaded`. Тесты — `tests/test_rerank.py`.

Авторский прогон 05.11.2026 (CPU, 4 потока, около 25 минут, почти всё — 4608 пар cross-encoder). Нужный документ первым на 24 перефразированных вопросах:
- после лексической стадии — 11, с эвристикой 12, с cross-encoder 22 при 23 в пуле;
- после MiniLM — 4, 8 и 15 при 17 в пуле;
- после USER-bge-m3 — 19, 18 и 22 при 23 в пуле.

Без первой стадии, по всем 72 фрагментам, — 23 из 24. Около 4 пар в секунду: пул из 20 — 4.9 с на запрос. Sigmoid от лучшего логита не выше 0.001 у четырёх вопросов без ответа, но 25 из 60 вопросов с ответом получили меньше 0.5, а самый низкий — 0.0006. Метрики ранжирования совпали с предварительным прогоном до последнего знака; задержка отличалась в пределах 0.1 с. Это синтетический корпус, а не оценка модели.

## Дополнение версии 1.2.0: контекст для фрагмента (T36, расширение M10-L01)

```powershell
.\.venv\Scripts\python.exe labs\M10\contextual_retrieval.py
```

Нужны llama.cpp и GGUF из T30 (`labs\M09\llama_local.py fetch`, `tools\download_models.py --gguf`); новых загрузок и пакетов нет. Корпус и вопросы — из T32: 72 абзаца, 24 перефразированных вопроса, 24 с термином, 12 вопросов 1.1.0. Контекст к каждому абзацу пишут Qwen2.5-0.5B и Qwen3.5-4B через llama-server. Метрики документные: R@1, R@3, R@20, MRR, а `first_ranks` даёт ранг по каждому вопросу. Контексты сохраняются в `artifacts/M10/contextual/contexts-*.json` вместе с хешем корпуса. `--reuse-contexts` повторяет поиск без генерации, `--no-4b` берёт только 0.5B.
