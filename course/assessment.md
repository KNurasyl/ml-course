# Как проверять результат и решать, можно ли двигаться дальше

Версия 1.1.0. Эти условия применяются к каждому уроку, домашней работе и проекту. Самопроверка не требует подтверждения наставника. Результат автора лабораторной не является твоим результатом.

## Три обязательных условия

1. **Корректность:** все обязательные условия задачи выполнены, нет критической ошибки. Для кода это также неверные входы, повтор, границы и сохранение инварианта, если они входят в контракт.
2. **Понимание:** без открытого решения ты можешь объяснить механизм, одно промежуточное вычисление, причину выбранного ограничения и новый случай. Рабочий код с неверным объяснением не выполняет это условие.
3. **Самостоятельный перенос:** после подсказки или полного ключа решён другой вариант без содержательной помощи. Повторить уже прочитанные строки недостаточно.

**Эти условия нельзя компенсировать суммой баллов.** Ни 8/10, ни красивый отчёт не дают самостоятельный зачёт при невыполненном условии. Баллы предметной рубрики помогают найти пробел; состояние навыка определяется условиями выше. Существенная помощь относится к попытке, а не навсегда к человеку: новая самостоятельная попытка может подтвердить навык.

В начале задачи прочитай её контракт и критерии, но не открывай ответ. После первой попытки проверь конкретные результаты. Для открытого проекта сравнивай своё решение с требованиями и разборами альтернатив, а не с единственным именем библиотеки в эталоне.

## Семь разобранных примеров оценивания

| Наблюдаемая работа | Состояние | Почему и следующий шаг |
|---|---|---|
| Код корректен, объяснение верно, новый вариант выполнен без помощи | Самостоятельно — самооценка | Сохранить работу и назначить другой случай через 3–10 дней |
| Верное решение получено после подсказки, указавшей нужный метод | С поддержкой | Не обнулять результат; дать новый вариант, в котором метод нужно выбрать самому |
| Программа выдаёт верное число, но ученик говорит, что RAG меняет веса | Требуется повторение | Повторить различие входа и параметров, объяснить изменение на новом примере |
| Высокая метрика после выбора признаков по test | Требуется повторение | Исправить процедуру; прежний test стал development, для независимой проверки нужен новый набор |
| Красивый отчёт утверждает, что новая модель быстрее, но время не измерено | Требуется повторение | Указать, что это гипотеза; выполнить сопоставимый опыт и ограничить вывод |
| Ученик воспроизвёл нехватку памяти, указал доступные ресурсы и предложил проверяемый малый вариант | Самостоятельно для навыка диагностики ограничения | Это не зачёт запуска конфигурации, которая не запустилась. Пройти малый обязательный вариант для соответствующего навыка |
| Старое решение ломается при новой категории; ученик только повторяет старый код | Требуется повторение | Найти изменившуюся предпосылку, исправить контракт обработки и пройти ещё один новый случай |

Правильность, помощь и устойчивость знаний — разные поля. Если код проверен, а объяснение ещё нет, состояние — «не проверено», а не «самостоятельно». Если тот же навык подтверждён новым вариантом спустя время, отметь «подтверждено позже — самооценка». Независимую проверку другим человеком записывай отдельно, только если она действительно состоялась.

## Как писать полезную обратную связь самому себе

Используй четыре предложения: **наблюдение → причина → исправление → новая проверка**. Например: «Recall упал на вопросах с отрицанием. Нарезка отделила “не” от условия. Я изменю разбиение по абзацам и сохраню оговорку вместе с правилом. Проверю ещё два отрицания, которых не было в настройке». Фраза «плохо понял RAG» не указывает следующего действия.

Полный ключ разрешён после сохранения попытки. После него открывай вариант B; если разобран и он, используй C. Если все фиксированные варианты уже знакомы, создай другой случай по шаблону в контрольной точке и проверь его по инвариантам. Не переименовывай знакомую работу в независимую.

## Что означают автоматические проверки

Команда в `exercises/Mxx/check.py` получает файл твоей реализации. Она проверяет конкретный контракт и специально подобранные ошибки. Полный запуск `tools/verify.ps1` проверяет авторские материалы. Ни одна из команд не устанавливает, кто написал код, можешь ли ты его объяснить и сохранился ли навык спустя неделю.

Встроенные стартеры намеренно содержат незаполненную функцию ученика. Это формулировка упражнения; обязательные объяснения, отдельное решение и проверка для неё должны быть готовы. Решение не лежит в стартере и не загружается проверкой как замена твоего кода.
