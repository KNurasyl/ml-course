## M11-L06-PF

Авторская проверка 06.11.2026 на сохранённых ответах прогона. Python (`contradicts` по ответам, прошедшим контракт): tiny — 2, strong — 0. Оба срабатывания tiny — «Ответ кандидата не верен.» с оценкой 2, на случаях c05 (эталон 2) и c13 (эталон 1).

Прямой перенос `/\bне\s*вер|\bневер/i` в JavaScript даёт 0 для обоих профилей. В JavaScript `\b` — граница между символом из `[A-Za-z0-9_]` и любым другим, даже с флагом `u` ([MDN: граница слова](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Regular_expressions/Word_boundary_assertion)). Пробел и «н» оба вне этого класса, поэтому граница перед русским словом не находится никогда. В Python модуль `re` для строк по умолчанию работает с Unicode, и `\b` видит границу. Исправление — `/(?<![\p{L}\p{N}_])(?:не\s*вер|невер)/iu`. С ним JS тоже даёт 2 и 0.

Assertion проходит, когда противоречия нет:

```js
const NEGATIVE = /(?<![\p{L}\p{N}_])(?:не\s*вер|невер)/iu;

function consistency(output) {
  const result = validateFeedback(output);
  const bad = result.valid && result.value.score === 2 && NEGATIVE.test(output);
  return { pass: !bad, score: bad ? 0 : 1, reason: bad ? 'score 2, feedback says wrong' : 'no contradiction found' };
}
```

Функцию добавляют в `module.exports`, а в конфиг — проверку `file://checks.js:consistency` с `metric: consistency`. Эвристика ловит слова, а не смысл: фраза «неверно было бы сказать…» тоже сработает. Поэтому оба срабатывания читают глазами. Критическая ошибка — поверить нулю JS-проверки, не сверив его с Python на тех же сохранённых текстах. Вторая ошибка — сверять на новой генерации: тогда расхождение модели не отличить от расхождения проверок.

## M11-L07X-A

Числа зависят от своего прогона, поэтому ключ проверяет ход решения. Авторская проверка 06.11.2026: в prompt «например [index-v2-c1]» заменено на «точно так, как id написан перед источником». Собраны те же 66 вопросов той же моделью и тем же поиском. Срабатывания проверок до и после:
- ссылка на пример из prompt — 24 → 1;
- неверная ссылка — 17 → 1;
- нет ответа — 43 → 12;
- нет отказа на вопросах без ответа в базе — 5 → 1;
- лишний отказ — 10 → 37;
- формат — 2 → 4;
- трасс без единой тревоги — 7 → 11;
- промах поиска не изменился — 6, поиск тот же.

Вмешательство убрало причину, которую нашёл разбор, но ошибки перетекли в соседний код. Модель перестала отвечать голыми ссылками и стала отказываться даже там, где ответ лежит в контексте. Трасса dev-cache, верная до вмешательства, теперь — отказ. Поэтому «стало лучше» нельзя решить по одной проверке: из 66 трасс без тревоги стало 11 вместо 7, но лишние отказы выросли почти вчетверо.

Ручное кодирование новых трасс нужно, потому что проверки придуманы по старым. Например, на вопрос без ответа модель ответила «Вопрос не содержит ответа.». Это отказ по смыслу, но проверка ищет точную фразу и засчитала его как «нет отказа». Следующая причина для разбора — лишние отказы: модель не находит ответ в контексте, который его содержит. Кандидаты — порядок источников, длина prompt и сама модель (сравнить с 4B). Критическая ошибка — объявить успех по падению одного кода, не посчитав остальные, и не перепроверить проверки на новых трассах.

## M11-L07X-B-C

B: коды — промах поиска, нет отказа, мимо вопроса и неверная ссылка. Первая ошибка по конвейеру — промах поиска: без нужного фрагмента в контексте всё остальное следствие. Сначала чинят поиск, затем учат модель отказываться при пустом контексте. Проверка «нет отказа»: точность 4 / 4 = 1.0, полнота 4 / 9 ≈ 0.44. Она не ошибается, когда срабатывает, но находит меньше половины случаев. Если проверка, как в лабораторной, знает только вопросы без ответа в базе, она пропускает трассы, где ответа нет из-за промаха поиска, и отказы другими словами.

C: трасса — вопрос и аудио кандидата, распознанный текст, найденные источники, prompt, ответ модели, синтезированная речь, задержки и идентификатор хода. Ожидаемые ошибки, например обрыв из-за перебивания, оценка без основания или ошибка распознавания отрицания, записывают отдельно до чтения. Затем читают все 60 сессий и кодируют без этого списка, а в конце сравнивают: что ожидалось и не встретилось, что встретилось и не ожидалось. Автоматическими разумно сделать дешёвые структурные проверки: звук отменённого хода после перебивания (по идентификаторам хода) и ссылка в отзыве на фрагмент, которого нет в ответе кандидата. Каждую сверяют с ручными кодами на сессиях, по которым её не придумывали. В регрессионный набор идут детерминированные части: обработка отмены хода, проверка схемы отзыва (M09-L08X), поиск по контрольным вопросам и опасные случаи, найденные разбором. Модель в быстрых тестах не вызывают.
