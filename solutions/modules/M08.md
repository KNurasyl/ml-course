## M08-L03-A

**1. Сравни запрос с ключами и учти размерность.** Скалярные произведения равны 1 и 0. Делим их на √2:

`scores ≈ [0,707107; 0]`

**2. Нормируй по ключам.** Возведи e в степень каждого score и раздели на общую сумму:

`A ≈ [0,669762; 0,330238]`

**3. Смешай values с найденными весами.** Первая координата приходит из v₁, вторая — из v₂:

`O = [2 × 0,669762; 4 × 0,330238] ≈ [1,339523; 1,320954]`

**4. Проверь формы для batch из условия.**

| Тензор | Форма | Проверка смысла |
| --- | --- | --- |
| Q, K | [2, 5, 3] | 2 последовательности, по 5 позиций, ключ ширины 3 |
| V | [2, 5, 4] | У каждой позиции 4 смешиваемых признака |
| scores, A | [2, 5, 5] | Каждая query сравнивается с 5 keys |
| O | [2, 5, 4] | Число queries и ширина values сохраняются |

Softmax по query нормирует вклад разных запросов в один key; строки могут не суммироваться в 1, поэтому исчезает заданная интерпретация смеси для каждого запроса. Тест должен проверять именно последнюю ось.

## M08-HW01

Эталон формулы: scores=Q@K.transpose(−2,−1)/sqrt(d_k); scores.masked_fill(upper_triangle,−inf); A=softmax(scores,dim=−1); out=A@V. Для батча[2,5,3] и V[2,5,4] выход[2,5,4]. Проверка A.sum(−1)==1 и A.triu(1)==0 обязательна. В численном примере L04 выходы[2,3,14/3,7,5], изменение последнего value не меняет первые 3.

labs/M08/demo.py содержит полноценный маленький causal Transformer и обучение. Словарь строится по train; отложены целые комбинации, а не перекрывающиеся окна. Baseline считает частоты train с add-one smoothing. Teacher-forced validation и свободные генерации сохраняются раздельно. Полученные значения отчёта относятся к данной грамматике и seed, а не к общему языковому качеству.

Для новой конструкции, например добавления наречия, расширь корпус и заново зафиксируй split/словарь. Если появились неизвестные токены, опиши UNK-политику вместо скрытого удаления строк. Корректный отрицательный результат — модель не справилась при заданных ресурсах — допустим, если механические тесты проходят и ограничения объяснены.

### M08: самостоятельная реализация масок, B и C

[Решение контракта](../exercises/M08/solution.py) сначала строит нижний треугольник causal, пересекает его с padding key-mask, проверяет существование доступного key, ставит −∞ до softmax и нормирует по последней оси. Затем A@V.

Проверка: `.\.venv\Scripts\python.exe exercises\M08\check.py solutions\exercises\M08\solution.py`.

B: перестановка доступных пар key/value вместе лишь переставляет слагаемые суммы для фиксированной query; causal-доступность при этом должна сохраниться. Переставить весь временной ряд без пересчёта mask — другая операция. C: при изменении будущего value ранние выходы неизменны; изменённый настоящий value последней позиции должен влиять на неё. Padding value не влияет ни на один выход. Полностью запрещённую строку отклоняем, а не выдаём NaN.

## M08-L01: B и C

**B.** Последовательность [3,1,2,4]; input до padding [3,1,2], target [1,2,4]. После дополнения input=[3,1,2,0,0], target=[1,2,4,0,0]. В loss входят позиции 0,1,2, включая предсказание EOS; PAD-позиции 3,4 исключены. EOS завершает текст, PAD выравнивает длину — это разные роли.

**C.** Добавляем UNK с ID=5, известные ID не меняются. «cad» с EOS кодируется [3,1,5,4], декодируется как «ca<UNK>» с маркером конца. Точный неизвестный символ утрачен: это мог быть d или другой символ вне словаря. Сначала разделяют независимые документы/группы, затем получают окна внутри каждой части; распределение перекрывающихся окон одного документа по train/test создаёт утечку.

## M08-L02: B и C

**B.** Нормы u и v равны 5, z равна 0. Скалярное произведение u·v=−25, cosine=−25/(5·5)=−1. Для z знаменатель нулевой, cosine математически не определён. Допустима явная ошибка/None с диагностикой или документированная численная конвенция с отдельным флагом; молчаливое 0 скрывает отсутствие определённого направления.

**C.** Векторы [1,0] и ([0,0]+[1,0])/2=[0,5;0], cosine=1. Простое среднее с данным словарём не сохранило отрицание. Проверять нужно размеченные поисковые пары, отрицания, язык и трудные отрицательные примеры, сравнивая с лексическим baseline. Случайные или произвольные token embeddings не становятся качественной семантической моделью от одного pooling.

## M08-L03: B и C

**B.** Scores=[ln(3),0], exp scores=[3,1], веса=[0,75;0,25]. Выход 0,75·[2,0]+0,25·[0,4]=[1,5;1]. После согласованной перестановки scores=[0,ln(3)], веса=[0,25;0,75], значения тоже переставлены; выход остаётся [1,5;1]. Перестановка только K без V меняет соответствие и не обязана сохранять результат.

**C.** Правильно по строкам: [[0,5;0,5],[0,75;0,25]], суммы [1,1]. Ошибочно по столбцам: [[0,25;0,5],[0,75;0,5]], суммы строк [0,75;1,25]. Для scores[query,key] нормируем последнюю ось key. У batched scores[B,Tq,Tk] это dim=−1, а dim=0 смешивал бы batch. Один тест суммы строк не доказывает правильность всех масок, но обнаруживает эту ошибку.

## M08-L04: B и C

**B.** Разрешённые ключи по строкам query: [[1,0,0,0],[1,1,0,0],[1,1,1,0],[1,1,1,0]]. Последняя query может обращаться к прежним непустым ключам; её выход не используется в loss. Цели B и EOS на позициях 0 и 1 участвуют; PAD на позициях 2 и 3 исключён. Key-padding mask и маска loss решают разные задачи, поэтому одна не заменяет другую.

**C.** Выходы позиций 0 и 1 обязаны совпасть: их допустимый префикс неизменён. Позиции 2 и 3 могут измениться. Существенное различие первых двух означает нарушение условий теста или причинности: проверь маску, ось softmax, отключение dropout и отсутствие перемешивания позиций в нормализации. Причинность задаётся структурой вычисления, а не выученной статистикой, поэтому случайные веса достаточны для теста.

## M08-L05: B и C

**B.** NLL_A=−(ln0,9+ln0,1)/2≈1,203973, perplexity_A=1/√0,09≈3,333333. NLL_B=−ln0,5≈0,693147, perplexity_B=2. Средняя вероятность теряет информацию о сильной ошибке с вероятностью 0,1; log-loss её штрафует. Эти значения относятся к двум фиксированным целям, а не ко всей языковой способности модели.

**C.** Teacher forcing на втором шаге использует правильный префикс [A,B] и оценивает C. Свободная генерация использует собственный ошибочный префикс [A,X] и получает Y. Модель попала в другое условное распределение; ошибки могут менять все дальнейшие контексты. По argmax нельзя вычислить perplexity: нужны вероятности правильных целей и маска оцениваемых позиций.

## M08-HW01: B и C

**B.** Без маски каждая строка весов [1/3,1/3,1/3], выход (2+4+12)/3=6. Правильные строки [[1,0,0],[1/2,1/2,0],[1/3,1/3,1/3]], выходы [2,3,6]. Нормировка проверяет распределение вероятностей, но не допустимость его носителя: вероятность будущих ключей может быть положительной при сумме 1. Нужны оба теста: суммы и нулевая масса на запрещённых позициях, плюс изменение будущего не меняет прошлое.

**C.** Строки весов [[1,0,0],[1/2,1/2,0],[1/2,1/2,0]], выходы [2,4,4]. Loss учитывает позиции 0 и 1 (B и EOS), PAD-цель 2 исключена. Замена PAD-value не меняет ни один из этих выходов, поскольку его key запрещён. В данном коротком causal примере первые две позиции и без key mask не видят будущий PAD, но последняя query увидела бы его; в иных схемах padding/батчей это загрязнение может затронуть используемые выходы. Маска loss исключает цель из оценки, но сама не запрещает читать её вход как key/value.

## M08-L08X-A

Блок обучает четыре токенизатора на обучающей части и считает n-граммные модели на тесте. Модель GPT для него не нужна, на CPU он идёт около 20 секунд.

```python
import importlib.util
from collections import Counter
from itertools import pairwise

spec = importlib.util.spec_from_file_location("gpt_from_scratch", "labs/M08/gpt_from_scratch.py")
lab = importlib.util.module_from_spec(spec)
spec.loader.exec_module(lab)

parts = lab.corpus()
nbytes = sum(len(d.encode("utf-8")) for d in parts["test"])
print(f"{'V':>5} {'B/tok':>6} {'uni/tok':>8} {'bi/tok':>7} {'uni bpb':>8} {'bi bpb':>7} {'unseen pairs':>12} {'emb share d=352':>16}")
for vocab in (512, 1024, 4096, 8192):
    bpe = lab.BPE.train(parts["train"], vocab_size=vocab)  # the tokenizer sees the training split only
    train_ids, test_ids = bpe.encode_documents(parts["train"]), bpe.encode_documents(parts["test"])
    base = lab.ngram_baselines(train_ids, test_ids, len(bpe.vocab))
    seen = Counter(pairwise(train_ids))
    unseen = sum(pair not in seen for pair in pairwise(test_ids)) / (len(test_ids) - 1)
    share = vocab * 352 / lab.count_parameters(vocab, 352, 6, 256)
    print(f"{vocab:>5} {nbytes / len(test_ids):>6.3f} {base['unigram']:>8.3f} {base['bigram']:>7.3f} "
          f"{lab.bits_per_byte(base['unigram'], len(test_ids), nbytes):>8.3f} {lab.bits_per_byte(base['bigram'], len(test_ids), nbytes):>7.3f} "
          f"{unseen:>12.1%} {share:>16.1%}")
```

Числа автора на корпусе коммита 57486b8, на котором обучались модели урока. Этот ключ и страница модуля сами входят в обучающую часть, поэтому на текущем курсе числа немного сдвинутся.

Loss на токен, наты:

| Словарь | Байт на токен | Униграмма | Биграмма |
| --- | --- | --- | --- |
| 512 | 2.635 | 5.504 | 3.255 |
| 1024 | 3.492 | 6.184 | 3.607 |
| 4096 | 5.251 | 6.948 | 4.887 |
| 8192 | 6.071 | 7.149 | 5.725 |

Биты на байт, доля пар токенов теста, которых не было в обучающей части, и доля эмбеддингов в GPT с d = 352:

| Словарь | Униграмма | Биграмма | Новые пары | Эмбеддинги |
| --- | --- | --- | --- | --- |
| 512 | 3.013 | 1.782 | 0.7% | 2.0% |
| 1024 | 2.555 | 1.490 | 3.1% | 3.8% |
| 4096 | 1.909 | 1.343 | 14.7% | 13.8% |
| 8192 | 1.699 | 1.361 | 21.9% | 24.2% |

Как читать результат:
- **Loss на токен растёт со словарём** у обеих моделей: у биграммы от 3.26 до 5.73. Токен длиннее, и угадать его труднее. Если судить по этому числу, лучший словарь — 512, и это ловушка.
- **Биты на байт показывают обратное.** У биграммы 1.782, 1.490, 1.343, 1.361: минимум на 4096. Униграмма продолжает улучшаться и на 8192, с 1.909 до 1.699: ей нужны только частоты отдельных токенов.
- **Почему биграмма портится на 8192.** 21.9% пар токенов теста ни разу не встретились в обучающей части, при 4096 — 14.7%. Для них модель живёт на сглаживании add-0.1, то есть почти угадывает.
- **Выбор для GPT на 10 млн.** При 8192 четверть параметров уходит на таблицу эмбеддингов, а редкий токен за 444 тыс. токенов обучения встречается считанные разы и почти не учится. При 512 эмбеддинги дешёвые, но токен короче в два раза, и в окно 256 помещается вдвое меньше текста. 4096 — разумный компромисс для этого корпуса. Биграмма — только указание, а не доказательство для GPT. Проверка — обучить small с двумя словарями на одинаковое число байт, а не шагов: при меньшем словаре один шаг покрывает меньше текста.

Критические ошибки: сравнивать словари по loss на токен; обучать токенизатор на тесте или на всём корпусе; передавать в `ngram_baselines` размер словаря без служебного токена; выбирать словарь по тесту, а потом на нём же сообщать итог.

## M08-L08X-B-C

**B.** Биграмма со словарём 512: 3.255 · 54 897 / (ln 2 · 144 669) = 178 690 / 100 277 ≈ 1.782 бита на байт. GPT plan: 3.255 · 27 552 / (ln 2 · 144 669) = 89 682 / 100 277 ≈ 0.894. Loss на токен одинаковый, а GPT кодирует текст вдвое плотнее: её токен вдвое длиннее. Параметры small: 4096 · 128 + 256 · 128 + 4 · (12 · 128² + 13 · 128) + 2 · 128 = 524 288 + 32 768 + 4 · 198 272 + 256 = 1 350 400. Эмбеддинги токенов — 524 288, это 38.8%. По правилу Chinchilla ей нужно 20 · 1 350 400 ≈ 27 млн токенов, в 61 раз больше обучающей части курса.

**C.** Разумный план:
- **Данные.** 20 · 10.48 млн ≈ 210 млн токенов. При 5.25 байта на токен это около 1.1 ГБ русского текста — в 400 раз больше, чем весь курс.
- **Время.** 210 млн / 1699 токенов в секунду ≈ 124 000 секунд, около 34 часов на CPU автора за один проход. Это выполнимо, но проверка, ранняя остановка и повтор при ошибке удвоят срок. На одной GPU уровня курса тот же объём обучается за часы.
- **Лицензии.** Подходят только тексты с явной лицензией, например дампы русской Википедии под CC BY-SA. Для каждого источника записывают лицензию и требования к атрибуции. Чужие курсы, книги и сайты без разрешения не берут.
- **Что получится.** Модель на 10 млн параметров и по правилу Chinchilla останется слабой: она научится грамотному тексту, но не знаниям и не рассуждению. GPT-2 small — это 124 млн параметров.
- **Путь для тренажёра.** Дообучение готовой модели из M12 даёт знания и язык сразу, и для него нужны сотни примеров, а не гигабайты. В курсе LoRA обучается на SmolLM2-135M на CPU, а с QLoRA на видеокарте так дообучают и модели в несколько миллиардов параметров. Обучение с нуля нужно для понимания механики и стоимости, а не для продукта.
