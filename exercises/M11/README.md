# M11: сравнить две системы по одним случаям

Версия задания 1.1.0. Сначала скопируй `starter.py` в `submissions/M11-HW01/` и реализуй контракт `compare_pairs`. Не открывай решение до сохранения попытки. Запуск из корня курса:

```powershell
.\.venv\Scripts\python.exe exercises\M11\check.py submissions\M11-HW01\starter.py
```

Проверяются порядок строк, пропуски, дубликаты, недопустимые типы и критическая регрессия при росте среднего. Это вычислительная часть: объяснение и независимость отмечаешь отдельно. Проектная часть — [полный протокол M11](../../course/lessons/M11-L06.md).

**Вариант B после разбора:** A: p=2,q=0,r=1; B в другом порядке: r=0,p=2,q=2. Критическая ошибка появилась в p, хотя его балл не изменился. Запиши оба вида регрессии и решение о выпуске. **Вариант C через неделю:** в B отсутствует q. Нельзя считать его нулём или удалять из A; покажи, что сравнение отклонено до вычисления среднего. Затем добавь явно размеченный q=0 и пересчитай.

После собственной попытки: [код решения](../../solutions/exercises/M11/solution.py) и [разбор вариантов](../../solutions/modules/M11.md). Для новой оценки после полного ключа используй C, сохрани полученную помощь и объясни, почему отсутствие оценки отличается от плохой оценки.

## Дополнительные упражнения (версия 1.2.0)

Ещё два контракта по урокам M11-L01, M11-L02, M11-L04, M11-L05 и M11-L06. Скопируй стартер в `submissions/M11/` под тем же именем, реализуй функции и проверь:

```powershell
.\.venv\Scripts\python.exe exercises\M11\check_ex02.py submissions\M11\ex02_agreement.py
.\.venv\Scripts\python.exe exercises\M11\check_ex03.py submissions\M11\ex03_release.py
```

| Упражнение | Уроки | Что реализовать |
| --- | --- | --- |
| `ex02_agreement.py` | M11-L01, M11-L02, M11-L04 | Coverage, accuracy среди ответов, корректные от всех и уместные отказы; согласие judge с ручной разметкой, где invalid остаётся в знаменателе; Cohen's kappa для любых меток |
| `ex03_release.py` | M11-L05, M11-L06 | Парный bootstrap по сценариям с заданными индексами пересэмплов; правило допуска M11-L06 с причинами блокировки в фиксированном порядке |

Как устроена проверка. Числа сравниваются с допуском. Kappa и agreement среди валидных сверяются со scikit-learn на случайных входах, bootstrap — с отдельным расчётом в цикле. Свойства: correct_total = coverage · accuracy, а success складывается из верных ответов и уместных отказов; correct_over_all = coverage · agreement; kappa симметрична, не зависит от имён меток и равна 1 при полном согласии; обмен версий меняет знак разницы и переворачивает интервал, а удвоение перефразирований одного сценария не меняет его вес; каждая причина блокировки появляется ровно тогда, когда нарушено её правило, а граничные значения порогов выпуск не блокируют. Пропущенная оценка — ошибка входа, а не ноль. Случаи с нулевым знаменателем — прогон без ответов, без отказов или без валидных оценок — и kappa при p_e = 1 проверка намеренно не задаёт: это вопросы вариантов C уроков M11-L01 и M11-L02, реши их сам. `--seed 7` даёт новый набор случайных входов. Часть случаев скрыта в `tests/hidden/` — по правилам самопроверки их не открывают.

Зелёная проверка подтверждает поведение функций, но не понимание: после неё объясни в журнале, почему стратегия «всегда отказываться» безопасна по ошибкам, но бесполезна по coverage, и почему bootstrap пересэмплирует сценарии, а не строки. Эталоны — [ex02](../../solutions/exercises/M11/ex02_agreement.py), [ex03](../../solutions/exercises/M11/ex03_release.py); открывай их только после своей попытки.
